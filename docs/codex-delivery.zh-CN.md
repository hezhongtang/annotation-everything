# Codex 桌面自动接入验收

2026-11-02 在 macOS 25.6 arm64、Codex 桌面 26.1027.51404 上，用 `fixtures/sample/` 的虚构材料验证。审阅、台账、批注和浏览器均隔离；原始接手证据保存在受控本机目录，不提交聊天身份、个人路径或业务材料。

## 实际空闲与普通重启

每次先准备合成批注，再由用户明确允许的一次性 Playwright 验收脚本等待聊天的 `task_complete` 事件。静默 3 秒并确认没有新轮次后，脚本实际点击网页的“交给 Agent”。这是有界的验收脚本，不是产品定时任务。两次提交均自动开始不同的新聊天轮次，执行 `ack`、按批号 `claim`、逐条 `resolve` 和 `done`；没有用户补发提醒。

时间为 UTC+8：

| 阶段 | 上一轮结束 | 网页点击 | 新轮次开始 | 结果 |
|---|---|---|---|---|
| 第一次空闲提交 | 10:31:43.019 | 10:31:46.223 | 10:31:46.530 | 第 1 批接手并处理完成 |
| 普通重启后的空闲提交 | 10:33:59.020 | 10:34:02.136 | 10:34:02.282 | 第 2 批接手并处理完成 |

两次之间停止本份合成审阅的服务，再仅用 `serve.py REVIEW --no-open` 启动。进程身份改变、绑定文件哈希不变、原专属端口恢复、`hook=true`；没有再次传 `--on-handoff` 或重新绑定。投递实现 `scripts/wakeup.py` 的 SHA-256 为 `f4ca270ea2dd7dedec0c818c98bb31afb412929d218f305da116767ef2c027c1`。后续补充的未知回执诊断未改变该投递实现。

## 回归与状态边界

- 自动化合成用例覆盖 HTTP 提交、实际 hook 子进程、本机 socket 协议、普通 CLI 重启、未发送提交恢复、重复抑制、明确拒绝后的重试、发送结果未知时不重放、身份校验和认领型 waiter 的冲突。
- `accepted` 只证明桌面接受投递；`received` 证明绑定聊天执行了接手确认。两者都不代表批注已经完成，完成结果仍看批次记录。
- 没有接手回执的已认领批次显示“接手未确认”。诊断的 `receiptConfirmed=null` 表示未知；不能据此断言离线，也不自动抢占、退回或重新认领。
- 忙碌接收另于 10:45:31 通过同一 HTTP 提交接口实测：聊天仍在原工作轮次时收到第 3 批消息，回执的轮次标识与提交前相同，随后完成认领、处理和收尾。此项验证当前轮次接收，不宣称已验证所有宿主的队列策略。

## 适配限制

适配器使用已有桌面的本机 IPC，不修改 Codex 全局配置、应用文件、权限或模型，不启动替代 CLI Agent，不创建定时任务或开机服务。该 IPC 不是稳定公开 API；实测版本之外须重新验证，不能承诺跨版本永久兼容。

桌面退出、聊天没有 owner、协议不兼容时保留批注并显示失败。发送后丢失回复或进程中断留下 `unconfirmed` 时，先核对聊天和批次，不盲目重发。绑定审阅移动或复制后必须重新核对身份。服务重启恢复尚待接收的事件，不接管别人已认领的工作。操作步骤见[Agent 机制](../skill/annotation-everything/references/agent-mechanisms.zh-CN.md#codex-桌面审阅级事件接入)。
