# 分析放在审阅里，轮次单独排队，结论只通过批注改稿

审阅人在批注过程中经常深入到某个问题后就迷失了，回头也看不到当时问过什么、答了什么、依据哪些假设。所以我们在审阅里加了第二种工作模式「分析」：围绕一个焦点问题按轮次追问。问答原文、决策、假设和检查点以只追加的事件日志存放在审阅目录里，当前状态由日志推导，被改写的只是推导出的状态，日志本身不改。分析不直接改报告；结论要先转成批注，经审阅人确认，再走「交给 Agent 改稿」这条唯一的改稿通道。分析轮次复用这份审阅的接收方绑定，但有自己的队列和事件类型，不进入批次队列。

## Considered Options

- **分析独立于审阅**：没有报告也能用，但要另建存储、台账和服务入口，跟批注的连接也会变弱。
- **在聊天里问答，页面只负责回看**：开发最省事，但记录要靠 Agent 转述，失去「保存审阅人原话」这一核心价值（与「Agent 收到的是原始批注，而不是转述」是同一个原则）。
- **轮次放进现有批次队列，用一个字段区分**：改动最小，但旧版等待进程和旧 Agent 会把一轮回答当成一批批注去改稿。
- **分析结论直接改稿**：路径最短，但会出现第二条改稿通道，处理记录和全量勾稽也都要分成两套。
- **一个提交按钮自动路由**：两边都有待处理内容时，一次点击会把改稿和答题一起发出去，审阅人看不出这次到底交了什么。
- **勾选全量勾稽就允许 Agent 改写「结论已变」的批注**：曾被采纳，复核后推翻。反例：在一条分析线上转出批注，切到另一条线，只为核对数字而勾选全量勾稽，Agent 就会按新线的决策改写这条批注并改稿；再切回原线时，批注又失效，而报告不会退回。勾选全量勾稽不应附带改写审阅人原话的授权。
- **批注侧用一个独立字段表示「暂不提交」**：不动状态取值，改动小，但旧服务读不懂，会把这些批注带进批次。

## Consequences

- **按钮**：两种模式各用一个按钮。批注模式的「交给 Agent」改名「交给 Agent 改稿」（Hand to the agent for revision），分析模式用「交给 Agent 分析」（Hand to the agent for analysis）。两个队列分开排队、互不合并，按交出先后处理。审阅人发起分析时，页面交出开题请求，Agent 据此出第一轮。
- **批注侧**：批注新增「搁住」状态并记录原因，原因有「分析中」和「结论已变」两种。旧服务生成提交快照时只收 open 状态的批注，所以搁住的批注不会被它带进批次。但旧页面会把认不出的状态改回 open，因此新功能上线后必须重启服务、刷新页面，新页面检测到服务不支持分析时提示升级。
  - 已被 Agent 领取的批注不能引出分析；只在待领取批次里的批注被引出分析时，待领取批次刷新快照，把它移出。
  - 结论转出新批注并经审阅人确认后，源批注标为已处理，并指向这个分析。
  - 分析里保留源批注的原文副本。
- **全量勾稽**：扩展为同时对照各分析当前分析线上的结论，但只列为待确认事项，不改写任何批注，也不回改已处理的稿件。需要列出的有四类：「结论已变」的批注、依据已失效的已处理批注、报告与当前决策矛盾而没有对应批注的地方、两个分析的结论互相矛盾的地方。
- **问题树与分析线**：
  - 问题树结构由 Agent 提议，审阅人在轮次中确认后才生效；死局提议同样作为轮次中的一项由审阅人确认，确认后拦住三类操作：改选到死局选项、在轮次里回答死局选项、切到死局线或从它的检查点分出新线。分析由审阅人发起，Agent 只能建议；分析不能删除，只能结案。
  - 「断枝」（对一个节点重裁）和「分析线」（从检查点整体回到当时的状态）是两个概念，不合并。
  - 分析线由分叉时的检查点加之后的增量构成，继承来的节点、决策和假设保留原标识，问题树结构按线保存。
  - 查证事实和「假设不成立」跨线共享，假设的确认按线记录；问题树上的死局也跨线生效。
  - 推翻假设时，如果当前线上有决策直接依赖它，就不在原线上逐级标记待复核，而是从推翻前的快照自动分出新线并切换过去：直接依赖的决策撤下重问，其下的子树暂成断枝，重新作答时选回原选项，下面的决策随之复活。旧线原样保留，标为「建立在已推翻的假设上」，作为当时推理的记录。如果当前线上没有决策直接依赖这个假设，就只标记不成立，不分线。
  - 批注是否「结论已变」只按当前分析线判断；依据重新生效时（切回原线、断枝复活），批注自动恢复未处理。
  - 这些规则用逻辑原型（`prototype/analysis-model` 分支的 `prototypes/analysis-model.prototype.html`）的 9 个情形验证过（102 个可见步骤，另有 102 个快进用的预置步骤），每一步的成功或被拒都符合预期。
- **并发**：每一轮带分析标识、分析线标识和基线版本号，回答按题目幂等。基线版本是整个分析共用的，锁定范围与它一致：Agent 领取一轮后、写回下一轮前，整个分析只能看和作答，所有分析线上的重裁、切线、分线、封存、推翻假设、请求更新批注、结案都被拒绝。最初只锁被领取的那条线，复核时实测发现：在另一条线上重裁会让基线变化，导致这一轮的结果被拒收、回答丢失，所以改为锁整个分析。写回时基线不符仍然拒收，作为多个标签页同时操作或断线补传的兜底；拒收后系统自动请求重新出题，并把这一轮已答、仍然有效的回答预先填进新一轮。
- **接收与投递**：
  - 轮次号在整份审阅内唯一，避免与批次投递撞键。
  - 投递分析事件时使用专门的提示，不要求改稿和重建。
  - 唤醒的事件类型、`notes.py wait`、投递状态徽标、`serve.py check` 都要扩展。
  - ADR 0004 的改绑规则扩展到轮次：有处理中的轮次时，不能更换或解除接收方。
- **数据**：
  - 问答记录不沿用批次的 200 条、处理痕迹的 50 条这类截断。
  - 页面引用按页面键保存，报告重建后仍能对上。
  - 文件模式（无本地服务）不提供分析。
  - JSON 导出不再是审阅的完整备份，需要在格式文档里写明。
- **范围**：「需要查证」默认只查审阅的原始材料；要查外部资料，须审阅人在该题明确允许。
