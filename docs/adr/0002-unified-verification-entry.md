# 统一验证入口独立于 ae.py

验证要留下可比较的证据：输入指纹、环境、逐用例耗时、结论和退出码都得能跨阶段读。这件事和 `ae.py` 的产品管理职责差别足够大，所以验证入口是仓库根目录下一个独立的 `verify.py`，`ae.py` 不动。

## Considered Options

- **并进 `ae.py` 加一个 `verify` 子命令**：入口数量最少，但 `ae.py` 的输出要走中英双语、围绕技能副本和本机台账，验证入口面向的是仓库检出（技能副本还没装也能验证）。两者生命周期不同：`ae.py` 随版本发给用户，验证入口只服务仓库开发。合到一个文件里，一个文件要同时背产品 CLI 和开发 CLI 的兼容责任。
- **放到 `tools/` 下**：`tools/` 已有开发工具，但 `tools/setup-dev.sh`、`tools/grade_iteration.py` 都不是每次开发都要敲的命令；验证入口是高频命令，放在根目录和 `ae.py` 并列更容易被发现，也和 README 的「开发」小节对齐。
- **独立根目录文件 `verify.py`（采用）**：与 `ae.py` 风格一致——`main(argv=None)` 返回退出码、命令行用错返回 2、模块 docstring 写用法；运行时只用标准库，语法兼容 Python 3.9。输出只要中文，和 `tools/` 下的开发工具一致，不引入第二套界面语言机制。

## Consequences

- 验证记录写在 `.verify/`（已被 `.gitignore` 忽略），本地留存，CI 作为构件上传；记录里不落本机绝对路径、不落环境变量原值。
- 用例级计时靠一个内部子命令 `_unit-runner` 在被测进程里跑，不把纯逻辑测试拆成独立进程；采集开销实测约 0.001%。
- `plan` / `run` / `report` 三个行为共用同一份组定义，报告只读记录、不启动产品测试。
- 原来的直接命令继续有效，退出码语义一致；唯一例外是空集合，直接跑 `unittest` 返回 0，入口返回 1。
