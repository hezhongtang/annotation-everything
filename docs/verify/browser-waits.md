# 浏览器等待的可观察状态改造（issue #54）

浏览器端到端入口 `tests/e2e_browser.py` 原有 96 处 `page.wait_for_timeout(...)`
固定等待（采样提交 `a3f9e1d1`，父规格 #49 的诊断口径）。本次按「等待证明的行为」
逐处替换为可观察状态条件；完整行为矩阵不变（13 个场景、629 项检查，与 #53 交付
的逐场景计数一致，无去重变化）。改造后 `e2e_browser.py` 仅剩 3 处有因保留的固定
时间（见「保留清单」），等待逻辑本身在 `tests/e2e_waits.py`（只依赖标准库，可被
单元测试以合成 stub 验证；playwright 仍只在 `e2e_browser.py` 导入）。

## 替换原则与机制

按等待的真实目的选择机制，不按文本批量缩短数值：

| 等待目的 | 证明的行为 | 替换后的机制 |
| --- | --- | --- |
| 普通 UI 就绪 | 动作的同步结果已呈现（列表重绘、弹窗打开、徽标变化、翻页） | `wait_for_function`（浏览器侧自动重试断言），条件全部取自页面自身状态：`#nlist` 卡片数、`#toast` 文案、`#mode` 类与文案、`localStorage ae.<RID>.page`、`#batches` 类等，未给页面加任何测试钩子 |
| 服务 / 文件状态同步 | 本次写请求已被服务确认并落盘 | Python 侧有界轮询磁盘（`wait_until`），绑定本次动作产生的具体内容（批注文本、skills.json 内容、handoff.json 的 seq / 字段），不接受动作前的旧状态 |
| 页面轮询周期 | 一次 `GET /api/notes` 轮询往返确实发生 | `page.expect_response` 事件等待（`wait_poll`），请求方法与 URL 精确匹配，完整往返（含应答）才通过 |
| 服务端修订推进 | 一次轮询把新修订应用到了页面 | 页面全局 `rev` 离开基线值（`wait_rev`），随后才检查「轮询不打断草稿 / 选择」类不变量 |
| 负面行为观察 | 不该发生的事情（写入被拒、CSP 拦截、无写请求）没有发生 | 优先绑定「拒绝确实到达」的正向事件（toast 文案、`server.log` 新增 `[reject]` 计数、POST 往返），再做负面断言；确无正向事件可绑定时保留有因固定窗口并记录预算 |
| 网络超时 / 断线 / 恢复 | 请求超时、断线、恢复补传这些时间边界事件实际发生 | 以事件结果为信号：断线 = 下一次轮询失败后徽标变化；请求超时 = 页面 8 秒上限走完后 `#mode` 转入待补传（上限 14 秒）；恢复 = 落盘 + 徽标恢复，全部有时间上限与超时诊断 |

超时契约（`e2e_waits` 单元测试覆盖）：等待必须有正的上限；超时输出场景 ID、
等待条件与最后观察到的状态（`[等待超时] 场景 …` 行，进入场景日志与 verify
记录）；被等待页面抛出的非超时异常原样传播，不被自动重试掩盖。

### 时间边界用例的事件证明对照

| 用例 | 改造前 | 改造后的事件证据 |
| --- | --- | --- |
| 跨过一次轮询后技能选择不丢（skill-search） | `wait_for_timeout(4500)` | `wait_poll`：等一次 `GET /api/notes` 完整往返，再按回车 |
| CLI 标已处理后轮询刷新不打断草稿（server-mode） | `wait_for_timeout(5000)` | `wait_rev`：页面全局 `rev` 离开基线，证明修订确实被轮询应用，再查草稿与焦点 |
| 认领状态重绘后用户展开的批次保持展开（server-mode） | `wait_for_timeout(4800)` | 先等 `#batchList` 出现「处理中」（只会随轮询应用的认领状态出现），再查展开状态 |
| 服务停止后提示未连接（server-mode） | `wait_for_timeout(4500)` | `wait_until`：下一次轮询连接失败后徽标出现「服务未连接」 |
| 服务卡死（SIGSTOP）请求超时转暂存（server-mode） | `wait_for_timeout(9500)` | `wait_until` 上限 14 秒：页面 8 秒请求超时真正走完、`#mode` 转入待补传才通过 |
| 恢复后补传（断线 / 写入失败 / 卡死 / 换审阅回切） | `wait_for_timeout(5500)` | `wait_until`：本次动作产生的具体批注文本落盘，且徽标恢复「已连接」/ 待补传清空 |
| 旧服务（功能剥离）判定就绪（full-check / handoff-i18n / server-mode） | `wait_for_timeout(1200)` | 徽标事件：只剥 full-check 时等「未连接 → 已连接」，剥掉 marks 时等 old 徽标 |
| 旧服务不确认全量勾稽（full-check 三例） | `wait_for_timeout(800)` | toast 事件（「本地服务不支持修改全量勾稽」/「服务未确认全量勾稽」）或 POST /api/handoff 往返 + 裁决结束 |
| 恶意网页写入全部失败（server-mode） | `wait_for_timeout(1500)` | `server.log` 中 `[reject]` 行数较基线增加（恶意请求确实到达并被拒），再断言什么都没写进去 |
| 孤立批注提示、对照页重建提示、技能目录应用 | `wait_for_timeout(4800/5000/4600)` | 轮询应用后的 DOM 事件（`#resume` 文案、`#reloadBtn` 可见、`skillCatalog` 含新技能） |

## 固定等待保留清单

不以「固定等待数为 0」为目标；以下是改造后保留的全部固定时间及其原因与预算：

| 位置 | 预算 | 对应行为 | 原因 |
| --- | --- | --- | --- |
| `locale-loop`（服务模式切语言） | 0.7 秒 | 「切换语言没有新的写请求」 | 负面观察窗口：必须给「假如切换会触发写请求」留出发火时间；0.7 秒覆盖页面 400ms 的草稿防抖定时器。切换语言的写请求（若有）在 change 处理器内同步发出，窗口结束后核对请求计数 |
| `file-mode`（注入内联事件） | 0.5 秒 | 「CSP 拦住注入的内联事件」 | 负面观察窗口：给无效 src 的 img 错误事件留出发火机会，证明内联处理器始终未执行 |
| `server-mode`（重建对照页前） | 1.1 秒 | 「重建后页面提示点此刷新」 | 跨过文件系统 mtime 粒度，保证 `build_viewer.py --rebuild` 产生的 indexMtime 变化可被轮询观察到（低速文件系统上同秒写入可能得到相同 mtime） |

此外两类「等待」不是固定等待，但与时间有关，一并说明：

- `wait_poll` / `wait_rev` / 各 `wait_until` 的**上限**（5–14 秒）是超时预算而非
  等待时长：条件满足立即通过，实测通常在数百毫秒内返回。
- `notes.py wait` 子进程的 `communicate(timeout=…)` 与 `start_server` 的就绪
  超时沿用 #51/#52 的受控参数语义，不在本次改造范围。

## 行为覆盖与稳定性

- 检查矩阵：基线与候选均为 629/629，`ok()` / `check()` 调用数逐一对齐
  （AST 口径 343 + 80 = 423 个调用；grep 口径的 344 + 94 含字符串与注释内出现），
  断言标签多重集逐一对齐，无断言删除、无检查去重。
- 受控重复（改造慢项，最终代码连续运行）：full-check ×2（16.8 / 16.8 秒）、
  server-mode ×2（53.5 / 53.5 秒）加 3 次完整回归，未观察到新增偶发失败；
  开发期间出现过的失败均已定位为本次引入的时序问题并修复（见 git 历史），
  无「首败被重试覆盖」路径——等待函数不重试被测操作本身，只重试条件探测。
- 超时诊断实测样本：开发中一次错误的就绪信号产生过
  `[等待超时] 场景 full-check：旧服务徽标出现（首次轮询按功能集判定）（上限 10 秒）；
  最后状态：mode='● 已连接（待补传 1）' toast=… handState=… nlist=…`，
  场景 ID、条件、最后状态齐备（该误信号随后按上表修正）。

## 已知限制

- skill-search 的时间边界用例证明的是「一次轮询往返确实到达」；页面侧
  `applyServer`（含列表重绘）在应答后的微任务里执行，极端时序下 Enter 可能落在
  重绘完成之前——该不变量的行使存在亚毫秒级空转窗口。基线的 4.5 秒固定等待
  覆盖更宽但同样不精确；`wait_rev` 在此不适用（该流程中服务端无待应用修订，
  rev 不推进），窗口保留为已知限制。
- 轮询类等待的下限由产品行为决定：恢复补传、认领状态重绘等仍需等到下一次
  4 秒轮询（0–4 秒抖动），属被测系统时序，不是测试垫等待。
- `wait_until` 的磁盘轮询步长 50ms，极端负载下 CPU 占用略高于旧的 200ms 步长；
  实测场景总耗时不升反降，未做进一步调优。
- 负面观察窗口（保留清单前两行）无法绑定正向事件，理论上存在「在窗口之后才
  发生违规」的漏检窗口；窗口预算按触发机制（同步处理器 / 400ms 防抖）取值。
- 性能对照在同机同日完成，未跨机器复现；`verify.py run --group browser` 会把
  逐场景 `seconds` 写入记录，后续 H 项可基于记录复算。
