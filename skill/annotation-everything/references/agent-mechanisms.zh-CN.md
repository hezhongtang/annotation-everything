# 各 Agent 的对应机制

首次配置接收批注或切换会话前，先读[接收方绑定与交接](receiver-binding.zh-CN.md)。确认接收会话后，再按宿主实际具备的能力选择事件接收、后台等待或轮询；`--by` 仅作处理署名，不参与身份校验。

[English](agent-mechanisms.en.md)

命令、文件和退出码对所有 Agent 一致。**不以宿主名称写死能力白名单，也不把「加载了本技能」或「启动命令返回 0」当作接手或唤醒能力证明。** 首次配置等待、调用批注技能、分派子代理或设置处理人前，先核对下表五项能力；权限、阶段停止和安全要求以[共用安全与协议约束](protocol.md)为准，完整操作顺序见[中文操作流程](workflow.zh-CN.md)。

## 先判能力，再选机制

| 能力维度 | 核对要点 | 对应做法 |
|---|---|---|
| **Shell 与命令** | 当前终端是 POSIX `bash`/`zsh` 还是 Windows PowerShell？ | POSIX 用 `python3 "$S/..."` 与 POSIX 引号；Windows PowerShell 用 `python "$S\..."` 与双引号/PowerShell 引号。路径含空格或中文时必须加引号，避免反斜杠被吞或单引号不兼容。 |
| **服务与等待进程存活** | 回合结束或沙箱退出后，后台启动的 `serve.py` / `notes.py wait` 是否继续存活？ | 若宿主允许同机持久后台进程，在绑定会话里后台启动并确认端口与状态文件；若宿主在回合结束或沙箱退出时清理后台进程，**不要凭启动退出码 0 判成功**——改由用户在独立终端运行 `serve.py`，并明确说明保持终端开启和重启条件。 |
| **等待、通知与事件接入** | 宿主是否提供（1）已验证的审阅级事件 IPC，（2）后台任务完成通知，或（3）外部触发钩子？ | 按实际可用最高能力选择：<br>1. **已验证的桌面事件 IPC**（仅已实测平台可用；Windows 首期不可用，`DesktopIPC` 会报 `desktop-ipc-unavailable`）：按下方事件接入流程绑定。<br>2. **有持久后台完成通知**：后台运行 `notes.py wait 审阅目录 --events analysis --harness ... --session ...`，由通知唤醒主会话后核对退出码和输出。<br>3. **无后台通知但可接外部事件**：用户启动服务时配置可信的 `serve.py 审阅目录 --on-handoff "命令 参数"`（不经 shell，Windows 同步等待子进程结束并保留退出码）。<br>4. **无通知也无事件接入**：用限时等待 `notes.py wait 审阅目录 --events analysis --timeout 30`（超时返回 3）或显式轮询 `notes.py claim 审阅目录 --events analysis`（有工作输出 JSON 并返回 0，无工作返回 3）。**明确提示用户保持当前会话/终端运行，或提交后返回聊天通知 Agent 处理**——不承诺任意真正空闲或已关闭聊天自动唤醒，也不通过未授权配置修改、计划任务或替代会话制造成功。 |
| **取消与停止响应** | 停止审阅或中断等待时能否可靠收尾？ | `notes.py wait` 收到停止信号（`SIGTERM` / `SIGHUP` / Windows `SIGBREAK` / `SIGINT`）清理 `.annotation-wait.<pid>.json` 并退出 `130`；收到审阅停止标志退出 `4`（不得当超时重新挂起）。不强杀归属不明的共享会话。 |
| **技能、子代理与问答工具** | 当前宿主有哪些工具？ | **调用技能**：使用宿主提供的技能加载工具按名称调用批注指定技能与常驻技能；若无专用工具则直接读取对应 `SKILL.md` 并执行，技能缺失时如实说明并按共用协议继续。<br>**子代理分派**：仅在批次 `allowSubagents` 为真且宿主支持子代理/多会话时分派（支持按阶段选模型时可用于初改与复核）；否则主会话亲自处理。<br>**问答工具（生成前对齐）**：有交互式问答工具时优先一轮收集缺失偏好与推荐项；无可用工具时先说明原因再用纯文本提问，并在 `request.qa.unavailableReason` 记明原因。<br>**`--by` 处理人**：按角色明确命名（如 `--by 初改`、`--by 复核`）；未传 `--by` 时，`notes.py` 仅在非空 `CLAUDECODE` 环境下缺省记为 `claude`，否则记为 `agent`。 |

## 界面、CLI 与投递状态口径

服务在线、投递被接受、聊天实际确认接手、处理完成是四件独立的事：

- **服务在线（`server`）**：只说明 `127.0.0.1` 本地服务可保存和读取批注，不证明接收方在线或会唤醒。
- **投递已接受（`accepted`）**：仅表示传输目标接受了投递请求，**没有确认回执不得显示或声称「已接手」**。
- **聊天实际接手（`received` / `ack`）**：仅在绑定聊天执行 `wakeup.py ack ...` 或实际 `claim` 后成立。
- **处理完成（`done` / `resolved`）**：批注和批次在 `notes.py` 落盘完成。
- **未知协议或未知宿主**：界面与状态汇总保留「接手未确认」或「接收方未知」，不假称离线，也不假称成功。

## 事件接入流程（仅在已验证平台可用）

用户要求网页提交后自动处理且当前宿主支持已验证的审阅级事件 IPC 时执行以下步骤；不要求用户修改宿主全局配置。**Windows 首期未提供/未验证 Codex 桌面私有 IPC**（执行 `bind` 会报 `desktop-ipc-unavailable`），请改用 `--adapter wait` 配合 `notes.py wait` / `claim` 或 `--on-handoff`。

1. 读取 `wakeup.py status 审阅目录`。已有绑定时沿用它，不把别的聊天或 Agent 自动改成新接收方。
2. 首次绑定：`wakeup.py bind 审阅目录`（POSIX 使用 `CODEX_THREAD_ID` 或 `--thread UUID`）。命令检查本机桌面 socket 和聊天 owner，把绑定保存到审阅旁的私有文件。`--by` 仅是署名，不参与路由。
3. 正常运行 `serve.py 审阅目录`。已有旧服务时先确认该进程属于本审阅且不打断其他人的处理，再停止、重启。后续普通重启自动恢复绑定，不需要重新传回调。自定义 `--on-handoff` 与保存的绑定冲突时拒绝启动；确需改接收方式时，用户决定后运行 `wakeup.py unbind 审阅目录` 并重启。
4. 事件消息送达后，先执行消息中给出的 `wakeup.py ack ...`，再运行消息给出的领取命令：改稿/复核用 `--seq N`，分析用 `--events analysis --round N`。分析轮次按[分析指引](analysis.zh-CN.md)处理，改稿/复核按已接收要求收尾。精确领取返回 3 时先处理真正队首，不绕过先前交出的任务。绑定模式不另开认领型 `wait`，也不创建定时任务。其他聊天不能通过新版 CLI 抢先 claim。
5. 验收包括真实空闲会话：上一轮已完成后，在合成审阅网页提交，确认聊天产生新的处理轮次，回写 ack、逐条处理和 done；正常重启同一服务后再次验证。忙碌会话接收消息、owner 查询成功或命令退出 0 均不足以证明空闲唤醒成功。

`wakeup.py status` 分开显示 `accepted`（桌面接受投递）和 `received`（聊天实际执行接手确认）；网页也显示这两个阶段。`failed` 可以在服务重启或用户再次提交时重试。`sending` 遭中断、或发送后丢失确认，会保留为 `unconfirmed`，须先核对聊天和批次，不能盲目重发。服务启动恢复待接收/待复核批次和排队的分析轮次，不抢占已领取的任务。

该适配器使用桌面现有本机 IPC，不改宿主全局配置、权限、模型或应用文件，不启动另一个 CLI Agent。IPC 不是稳定公开接口；当前实测环境仅为 macOS 桌面 26.1027.51404（Windows 桌面环境尚在 #177 实测前保持未验证）。桌面未运行、目标聊天无 owner 或协议不兼容时，明确报告接入失败并保留批注，不退回假成功。绑定仅适用于原审阅身份及目录；移动或复制后须核对并重新绑定。`unbind` 只解除接入，保留批注与投递历史。

## 总览首页代启动的接收

`serve.py overview`（可选 `--under 目录` 限定范围）打开独立的总览首页；对已停审阅点「启动并打开」由首页代为启动。首次打开首页前，按[启动总览首页](workflow.zh-CN.md#启动总览首页)完成能力探测。Agent 接收相关：

- 「交给 Agent」钩子只来自首页启动命令 `serve.py overview --on-handoff "命令 参数"`，绝不来自网页。新启动的审阅服务继承解析后的命令参数，并在首页启动时的工作目录下运行（不经 shell，参数里的相对路径按那个目录解析）。
- 已保存的接收方绑定与自定义钩子冲突时拒绝启动（原因码 `overview-hook-conflict`），绑定保持原样。要沿用绑定就不要带 `--on-handoff` 启动首页；要改用钩子先按[接收方绑定与交接](receiver-binding.zh-CN.md)解除绑定。
- 未指定钩子时按普通启动规则加载保存的绑定：启动只读绑定，不新建、改写或解除，也不代挂等待进程。
- 启动结果与审阅详情显示接收方式和绑定状态。等待型绑定显示 harness、会话与等待状态，并提供可复制的 `notes.py wait <标识前缀>`——从原绑定会话运行，身份沿用该会话的参数或环境变量。桌面事件绑定显示事件接收状态与会话，省略认领型等待命令。自定义钩子显示「已配置」。
- 复用已在运行的审阅服务时，结果显示该进程实际加载的接收方式；本次指定的钩子未应用会明确提示，无需替换正在运行的进程。
- 桌面绑定的启动补投与去重、继承钩子的触发时机都沿用现有规则：启动前已待接收、待复核的积压批次保留，可由 `notes.py wait` 或 `notes.py claim` 领取，不用钩子重放。

## 停止审阅与取消边界

`serve.py stop 审阅标识 --timeout 秒` 返回持久 JSON 状态；`stop 审阅标识 --status` 只查询。退出码 0 仅表示服务、等待者和该审阅后台工作全部确认停止，1 表示未完全停止，2 表示目标无效或有歧义。重复停止沿用同一 `stopId`，只补未完成组件；显式运行 `serve.py 审阅标识` 才重新接收工作，不归档、解绑、定稿或释放端口。

更换或解除绑定前，确认已投递且仍待领取的桌面轮次已取消。显式重新启动时，会重新投递已经确认取消且仍待领取的工作，包括复用在线服务时。

等待型 `notes.py wait` 因停止返回 4 并清理标记，不能把它当超时重新挂起。事件接收按审阅标识、接收方绑定和轮次标识取消；桌面接受请求、owner 查询、进程收到信号均不等于轮次已停止。宿主拒绝、超时或不能给出轮次终态时保留 `incomplete` 和能力缺口，不结束共享会话，也不强杀归属不明的进程。取消协议已由合成 IPC 覆盖，真实桌面宿主的取消能力尚未自动验证。

钩子的输入、运行目录和快照处理规则见[中文流程第 2 节](workflow.zh-CN.md#2-启动服务并挂起等待)。分派前按[第 5 节](workflow.zh-CN.md#5-先改后审两段流程)传递已接收要求、批号和技能，并保留主会话收尾与用户确认的阶段边界。
